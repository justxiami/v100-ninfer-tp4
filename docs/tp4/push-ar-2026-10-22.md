# One-shot push allreduce for V100 tp4 (2026-10-22)

一句话：把 1Cat 的 `sm70_cross_device_reduce_1stage_push` one-shot push allreduce 移植进 ninfer 的 tp4
（单进程 UVA），替换 NCCL 的 4.6 ms/decode 轮 allreduce。引擎级两臂 A/B（每臂 fresh 重启、客户端
decode tok/s 剔 ttft）：PUSH 154.2/151.7 vs NCCL 133.0/131.2 ⇒ **+15.8% decode，省 1.032 ms/token**。
+15.8% 正好落在 1Cat 参照的 +13~18% 带内。两次误诊已更正：①「IOMMU 判死」= `TpComm::create` 里
`std::move` 后访问空 `impl` 的 NULL 指针 bug；②「CUDA graph 捕获崩」= `push_ar_try` 换设备不还原当前设备
（停在 rank 3 → `cudaErrorInvalidResourceHandle`）。现役 decode 本就是 `--no-cuda-graph` eager。
教训：**kernel 绿灯 ≠ 引擎绿灯**，独立测试照不出设备泄漏。

## 1. 背景：NCCL 4.7 ms 杠杆

decode 线收口（2026-10-22）nsys 实测 NCCL（AllReduce 137 次/轮）占 8k 轮墙钟 4.71 ms（23%）。1Cat
参照不是 NCCL，是自研 push all-reduce。09-16 trace 实测 1Cat 在跑 `sm70_cross_device_reduce_1stage_push<4>`
27255 次、9.2 µs/次（我们 NCCL 33.2 µs/次，慢 3.6×）。换 push AR 估 **+13~18%**。风险低、有现成参照，先试。

## 2. 第一次尝试误诊「IOMMU 判死」

第一次移植的独立测试 SIGSEGV。当时归因「裸跨 GPU kernel 指针解引用被 IOMMU domain 堵死」，判死
（硬件约束、不是软件 bug）。**误诊**。真因：`TpComm::create` 的局部 `impl`（`std::unique_ptr<Impl>`）
在第 140 行被 `std::move` 进 `TpComm` 对象，move 后局部 `impl` 变 NULL。push buffer 代码用 `impl->`
（NULL 指针）访问 → SIGSEGV。调试打印 `impl=(nil)` 一锤定音。

修复：push buffer 代码里的 `impl->` 全改成 `comm->impl_->`（访问真正存在于 `TpComm` 对象里的 `Impl`）。

## 3. 引擎级崩溃真因 = 当前设备泄漏

NULL 指针修好后，push 臂在 warmup 崩：`scatter.cu:32: cudaErrorInvalidResourceHandle`。我一度归因
「push 核在 CUDA graph 捕获里失效」。**那个归因错了**：现役 ninfer 是 eager decode
（`~/ninfer_run.sh:197` `GRAPH=${GRAPH:-0}` → `--no-cuda-graph`，NCCL 臂日志 `graphs=0.00 MiB` 佐证）。
根本没捕获图。

真根因：`push_ar_try` 的 launch 循环逐 rank `cudaSetDevice`，结束后**当前设备停在 rank 3**。调用方
后续 op 在 rank 0 的 stream 上 launch，而 stream 属于设备 0、当前设备是 3 → `invalid resource handle`，
由下一个错误检查点报出。传输层其它换设备入口都有 RAII 守卫 `CurrentDeviceGuard`（tp_comm.cu:42，
用在 156/278/313 行），唯独 push 分支（allreduce.cu:423 直调 `push_ar_try`）没有。

为何独立测试测不出来：`tests/ninfer_allreduce_nccl4_test` 自己管理当前设备，所以 27 档指纹全绿也照不出
这个泄漏。教训：**kernel 级绿灯不等于引擎级绿灯**，换设备必须在引擎里验。

修复：`push_ar.cu` 加 `CurrentDeviceRestore` RAII（对齐 `CurrentDeviceGuard` 语义），`push_ar_try`
入口处声明（push_ar.cu:40-47/170）。读回断言在位。编译过（21:38，13 个 push_ar 符号）。

## 4. 引擎级两臂 A/B（实测）

口径：客户端 decode tok/s（剔 ttft，`gen_wall` = 首 token→末 token），`max_tokens=512` 英文 prompt，
temperature 0.6，同二进制同参数（`--tp 4 --spec mtp --draft-tokens 3 --lm-head-draft --vision
--no-cuda-graph`），**每臂 fresh 重启 ×2**，每次重启量一发。

| 臂 | boot1 | boot2 | 均值 | 每 token 墙钟 |
|---|---|---|---|---|
| PUSH (`NINFER_PUSH_AR=1`) | 154.2 | 151.7 | **152.95** | 6.538 ms |
| NCCL (`NINFER_PUSH_AR=0`) | 133.0 | 131.2 | **132.10** | 7.570 ms |
| Δ | | | **+20.85 tok/s = +15.8%** | **省 1.032 ms/token** |

- 臂内方差：PUSH 极差 2.5 tok/s（1.6%），NCCL 极差 1.8 tok/s（1.4%）；两臂不重叠 ⇒ 差异成立。
- ttft 两臂同档（0.143–0.155 s）⇒ prefill 未受影响，符合预期（480 KiB 块超 `kMaxBytes` 80 KiB，
  正确回退 NCCL）。
- +15.8% 正好落在 1Cat 参照的 +13~18% 带内——它的数字在我们 V100 上是真的。
- 与微基准对账：微基准省 8.79 µs/collective；要凑到 1.03 ms/token 需 ≈117 次 allreduce/token。与 nsys
  的 137 次/轮（2026-10-13）同量级，差异属 round/token 口径差，不是矛盾。

## 5. decode 2048 阶梯（push 臂，thinking=on）

口径：客户端 decode tok/s（剔 ttft），decode 2048 档，en/zh/mixed 各 2 reps，`--tiers 8000 --reps 1`
只带 1 个 8k warmup（避开冷启动污染，不跑 prefill 阶梯）。

| 语言 | client tok/s | engine tok/s | spec tok/round | spec 接受率 |
|---|---|---|---|---|
| en | **129.2** | 129.8 | 2.2 | 40.0% |
| zh | **132.1** | 132.7 | 2.2 | 41.6% |
| mixed | **136.6** | 137.2 | 2.3 | 44.3% |

8k warmup：ttft 2.0 s，prefill client 4074.3 / engine 4106.5 tok/s，needle hit。

**本表与两臂 A/B 不可直接比**：两臂 A/B 是 temperature 0.6（编码档）× 512 tok × 英文，spec 接受率更高
（greedy 易预测）⇒ tok/s 更高。本表 thinking=on（t=1.0 采样）⇒ MTP 接受率 40–44% ⇒ tok/s 更低。
**温度口径不同，两表分列，不混比**。

## 6. 与历史基线对账（decode_2048 长思考口径）

decode 线收口（push AR 之前，NCCL 路径）给出：decode_2048（长思考，低 α）tokens/round 2.0–2.2、
α 33–41%、decode tok/s **104–117**。push 臂落在 NCCL 基线之上 **+12~25%**（129–137 tok/s），α（40–44%）
在 NCCL 基线区间（33–41%）上沿——α 是采样制度的属性，同温度同 α，上沿散布是同条件多轮的散布。

从 tok/s 与 tokens/round 反推每轮墙钟：NCCL 2.1/108 = **19.4 ms**，push 2.25/133 = **16.9 ms**，
**省 2.5 ms/轮**。正好等于 nsys 账：NCCL 137×33.2 µs = 4.55 ms，push 137×9.2 µs = 1.26 ms，差 **3.3 ms**
——与实测 2.5 ms 同量级（差值来自 nsys busy 与墙钟口径）。关键反证：若 α 不变（2.1 tokens/round），
push 臂应是 2.1/16.9 ms = **124 tok/s**，仍比 NCCL 的 108 高 **+15%**。也就是说**哪怕 α 一点不升，
光 allreduce 省时就有 +15%**；实际量到 +19~25%，多出来的是 2.1→2.25 采样随机性（同条件散布），不是
allreduce 改了 α。**结论：同条件成立、α 没变，增益全来自 allreduce 每轮省时 2.5 ms**。

## 7. 事故：两头全空窗 11 分钟

`twoarm_v2.sh` 末尾「恢复 PUSH 臂为现役」复用了 `measure_rep`，而它测完会 `stop_serve`——本该留下的
现役服务被自己停掉。结果 :8901 与 :8095 从 21:50:16 到 22:01:16 双双无监听，全空窗 11 分钟。
`switch_to_ninfer_push.sh` 开的 1200s 独立看门狗（setsid）接住：22:01:16 发现两头全空 →
`bash ~/strata_run.sh` 顶回 strata（pid 177721）。脚本已修：新增 `start_only`（只起不停）并改末尾调用。

## 8. 用法

- **现役 push 臂**：`NINFER_PUSH_AR=1 bash ~/ninfer_run.sh`（起 push 臂）。
- **关回 NCCL 臂**：起服务时不带 `NINFER_PUSH_AR`（`bash ~/ninfer_run.sh`），不用重编。
- push 核只在 tp == 4 且单进程 UVA 下生效；480 KiB prefill 块超 `kMaxBytes`（80 KiB）自动回退 NCCL。
  decode 的 10 KiB 形态走 push 核。
- 切换/对照脚本：`~/bench-results/2026-10-22/push-ar/switch_to_ninfer_push.sh`、`twoarm_v2.sh`
  （已修 `start_only`）。
