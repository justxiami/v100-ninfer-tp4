## 3. 最终架构（实读代码后的真实形态）

- **权重**：`vision/*` shard → `Replicated` ⇒ 每卡一份完整副本（~0.3GB/卡）；
  `build_device_view(plan, rank, ...)` 按 rank 各自 materialize 到本卡（这是 4b 的修复点）。
- **编码**：全进程**只有一个** `VisionPrefillSession`（在 rank 0 的 prefill 驱动路径里建，
  `program_impl.h start_prefill_lane`），`context_.encode()` 跑在 rank 0 设备上 ⇒
  编码结果在 rank 0 显存（transient 区）。
- **media chunk（关键实现）**：`TextContext::prefill_impl_tp2` 新增 `multimodal` 分支：
  1. `prepare_chunk(text_kv_base, len)` → 可能**裁剪 len 到 item 边界**；返回
     `VisionChunk{length, control(scatter_indices), embeddings}`；
  2. 本 chunk 内媒体 token 的 scatter 相对索引（`local_scatter_indices` / `visual_begin`）；
  3. 每 rank 分配 roots：`rope_axes=3` + scatter_indices（工作区计划已含预算）；
     3 轴 RoPE positions 从 `multimodal->positions` 按轴拷到**每个 rank 自己**的 tensor；
  4. **rank 0**：embedding → `ops::scatter(embeddings, indices, x[0])`；**peers 跳过** x 构建；
  5. rank 0 的 scatter 完成后记 event → 每个 peer `cudaStreamWaitEvent(自己流)` +
     `cudaMemcpyAsync(x[peer] ← x[0], cudaMemcpyDeviceToDevice, 自己流)`（整块 [hidden,len]）。
- **为什么整块拷残差而不是让 peer 自己 encode 或读 peer 显存**：
  - 引擎的 `enable_peer_access()`（`src/ops/common/allreduce.cu:276`）**只对 tp==2 开**，
    tp4 没有 peer 访问 ⇒ kernel 直接读 0 号卡显存不可靠；
  - 复制残差走的是引擎既有模式（`resume_hidden` 的跨卡 staged copy 同款）；
  - 单次编码 = 各 rank 数值天然一致（避免 4 份编码的潜在 bit 差异）。
- **RoPE**：`rope_delta` 透传（每 rank `io.rope_delta`），rope positions 走 3 轴（媒体位置由视觉
  处理器给出），`active_rope_positions_` 与 peer 绑定都指向 3 轴 tensor。
- **MTP**：对齐段（`prepare_mtp_prompt`）照旧用 prompt token ids 走 tp2 的
  `mtp_prefill_chunk_tp2`（未做 shifted visual 部分，见 §4）。

## 5. 已知缺口（未做，按需再说）

1. **MTP 对齐段的 shifted 视觉 embedding——已补（2026-10-05 00:5x）**：
   `prefill_impl_tp2` 现在按 tp1 口径构建移位流的视觉 embedding
   （`shifted_visual_overlap` + `scatter_shifted_visual_embeddings`）：rank 0 embed+scatter，
   其余 **embedding 侧** rank（tp4 下 = rank 1）经事件排序的 D2D 拷贝拿到同一缓冲；
   hidden 侧 rank（2、3）不 embed。插桩实测 `overlap=240 scatter=240`（整块图的 240 个
   merged token 都落在 MTP 窗内）。
   **实测收益 ≈ 0**：同 6 变体配对 A/B（同一张图、每个变体都是 cache=0 全量 prefill）：
   WITH 2.890 tok/round vs WITHOUT 2.883 tok/round（+0.007，远小于 run-to-run 波动
   ±0.05–0.15）。原因判断：MTP stem 的 fc 输入是 `[embedding_norm | hidden_norm]` 各半，
   目标模型自己的 hidden 已携带图像语义，token embedding 侧只是另一半。
   结论：**保留**（与 tp1 语义对齐、成本可忽略、防长图/多图场景的潜在质量崖），
   但它不是掉速的成因。
2. **MTP bridge（prefix-reuse 用图）——已补**：
   原来 tp>1 下 `mtp_bridge_and_propose` 遇到媒体 bridge token 直接抛
   `tensor-parallel MTP bridge supports text inputs only`（= 请求 500）。
   现在同一套每 rank embedding 机制接进 `mtp_bridge_tp2`：rank 0 用
   `[hidden,1]` 的视觉 embedding，其余 embedding 侧 rank 经事件排序拷贝。
   （触发条件很窄：复用点必须正好落在媒体 token 上，含模板 token 时不会触发。）
3. MTP 的 rope positions 用 1 轴 cache positions（非 3 轴），仅影响 draft 质量，未动。
4. 视频不支持（用户口径只图像）；32768 merged 上限未动。
5. `35b_a3b` 目标也调 `materialize_vision_common`（其 loader 是单设备构造器，tp1 语义），
   未动；只有 27b（现役工件）修了 device 透传。
6. `serve_options.cpp` 的备份文件是**改后**状态（10/05 00:02:59 备份晚于 00:02 的编辑）——
   回滚它不是"恢复备份"，而是"按 §2 表重加门槛"。

## 7. 事故与教训（10/05 夜）

1. **切换脚本的 grep 校验写错一个字符**：`^BIN=\${BIN:-$NEW_BIN}}` 多了一个 `}` ⇒ 校验必失败 ⇒
   sed 明明改对了却"恢复备份"，把 `ninfer_run.sh` 留在"旧 BIN + VISION=1"的矛盾态，
   用户手动 `ninfer_run.sh` 自然起不来（旧二进制拒 `--vision`）。
   → 教训：校验命令写完先在 /tmp 副本上跑一遍（本次已补做，4 条全过）。
2. **用户手动拉起的 vllm 与 tp4 ninfer 抢 4 卡**：vllm TP4 每卡 15.1GB，ninfer 需要 ~14GB ⇒
   同卡不可能共存；"nigfer 起不来"的首因是显存，不是代码。切换前先看 `nvidia-smi` 与端口占用。
3. **切换脚本的健康等待有 420s 静默窗**：日志只有一行"起 unit..."，用户看到的是"卡住"。
   → 后续改进方向：把等待进度打到 stdout（低频）。
4. **停错东西的边界**：停 vllm 会让当前会话断（vllm 是手工进程，非 unit）——用"延迟编排 +
   后台脚本"（`/tmp/ninfer_vision_switch_orchestrator.sh`：15s 后杀 vllm → 等显存 → 切 ninfer）
   避开"回复发一半断线"。
5. **旧 BIN + --vision 的组合态**是本次 vllm/ninfer 事故的直接触点：
   BIN 与 VISION 两个开关必须一起改（switch/rollback 脚本已把它们绑成一个操作）。
